ADR-007: Package Structure and Testing

== Status
Accepted

== Context
Python package organization and testing strategies vary significantly:

**Package Structure Options:**
* Flat structure: All modules in root directory
* Nested modules: Complex hierarchical organization
* src/ layout: Industry standard for packaging
* apps/ with modules/: Domain-specific organization

**Testing Approaches:**
* No tests (dangerous for statistical software)
* Basic unit tests only
* Comprehensive test suites with fixtures
* Property-based testing for mathematical functions

Given that FHS performs statistical calculations that teams rely on for business decisions, testing strategy is critical.

== Decision
We will implement a *comprehensive testing strategy* with:

**Package Structure:**
```
apps/fhs/
├── src/fhs/              # Main package (src layout)
│   ├── models.py         # Core data structures
│   ├── monte_carlo.py    # Simulation engine
│   ├── risk_calculator.py # Risk calculations
│   ├── simulator.py      # Main orchestration
│   └── user_profiles.py  # UX simulation
├── tests/                # Comprehensive test suite
│   ├── test_models.py    # Data structure tests
│   ├── test_monte_carlo.py # Simulation tests
│   ├── test_risk_calculator.py # Risk calculation tests
│   ├── test_simulator.py # Integration tests
│   ├── test_user_profiles.py # UX simulation tests
│   └── conftest.py       # Shared fixtures
├── config/               # Configuration and dependencies
└── notebooks/            # Analysis templates
```

**Testing Strategy:**
* *165+ comprehensive tests* covering all modules
* *Parametrized tests* for different input combinations
* *Edge case testing* including empty datasets and extreme values
* *Statistical validation* for Monte Carlo accuracy
* *Reproducibility testing* with fixed seeds
* *Performance testing* for large dataset handling

== Consequences

=== Positive
* *High confidence* in statistical calculations
* *Regression prevention* - changes don't break existing functionality
* *Documentation through tests* - tests show expected usage patterns
* *Refactoring safety* - can improve code without fear
* *Standard Python packaging* - follows community best practices
* *Easy installation* - works with pip, poetry, conda

=== Negative
* *Development overhead* - tests take time to write and maintain
* *Test maintenance* - tests must be updated when behavior changes
* *Complexity* - new developers must understand test patterns
* *CI/CD dependency* - tests must pass before merging

=== Mitigation
* *Clear test documentation* - pytest conventions and fixture usage
* *Test utilities* - shared fixtures reduce duplication
* *Automated testing* - CI runs tests on every change
* *Coverage reporting* - identify untested code paths

    """Test that Monte Carlo results converge to expected values."""
    # Known analytical result for validation
    feature = Feature(name="Test", expected_users=1000, conversion_rate=0.15, uncertainty=0.0)  # No uncertainty
    result = simulator.simulate_feature(feature, scenarios=10000)
    expected = 1000 * 0.15  # 150
    assert abs(result.mean - expected) < 5  # Allow small variance
